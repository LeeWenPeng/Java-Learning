## 1  Java 对象的定位方式

Java 程通过栈上的引用 (reference) 数据来操作堆上的对象。对象的访问方式由虚拟机的具体实现来决定，只要有句柄和直接指针两种：

- **句柄**：在 Java 堆中会划分出一块内存作为句柄池，reference 中存储的就是对象的句柄地址。句柄中包含了对象的实例数据指针和类型数据指针，分别指向实例数据和类型数据各自的具体地址信息。
	- 使用句柄最大的好处是 reference 中存储稳定的句柄地址。在对象被移动时，只需要修改句柄地址中的实例数据指针，而不需要修改 reference 本身。
- **直接指针**：reference 中直接存储对象的地址。对象中包含对象的类型数据指针，这个指针指向对象的类型数据的具体地址。
	- 使用直接指针的好处是对对象的访问速度快，节省了一次指针定位的时间开销。
	- HotSpot 虚拟机主要使用的对象定位方式就是直接指针。

## 2  如何判断一个对象是否存活？

一般是通过引用计数法和可达性分析两种方式

- **引用计数法**：为每个对象分配一个引用计数器。每当有一个地方引用该对象时，计数器值加 1；每当有一个引用失效时，计数器值减 1。当计数器值为 0 时，表示该对象不再被任何变量引用，可以被回收。
	- 问题：**无法解决对象之间循环引用的问题。**
- **可达性分析**：通过一系列称为 **"GC Roots"（根对象）** 的起始节点，从这些节点开始向下搜索。搜索所经过的路径称为 **" 引用链 "（Reference Chain）**。当一个对象到任何一个 GC Roots 都没有引用链相连时，则该对象被判定为不可达（即不可用），可以被回收。

## 3  GC 是什么？为什么要 GC？

GC(Garbage Collection，垃圾回收) 是 Java 虚拟机提供的一种自动内存管理机制。它负责在程序运行过程中，自动检测并回收那些不再被使用的对象所占用的内存空间，使这些内存能够被重新利用。

内存处理是开发者最容易出现问题的地方，忘记或错误的内存回收会导致程序的不稳定甚至崩溃。Java 提供的 GC 功能将开发者从内存管理中解放出来，降低了编程复杂度，提升了开发效率。

## 4  可作为 GC Roots 的对象有哪些？

- 虚拟机栈中引用的对象：当前正在执行的方法中的局部变量和参数所引用的对象。
- 方法区中静态属性引用的对象：类的静态变量（`static` 字段）所引用的对象
- 方法区中常量引用的对象：
	- 被声明为 `final` 的常量值所引用的对象
	- 常量池中的字符串字面量（`String.intern()` 返回的引用）
- 本地方法栈中 JNI 引用的对象：也就是在 Native 方法中引用的对象。
- Java 虚拟机内部的引用：
	- 基本类型对应的 Class 对象：比如 `int.class`、`void.class` 等
	- 常驻的异常对象：比如，`NullPointException`、`OutOfMemoryError` 等异常类的预定义实例
	- 系统类加载器：启动类加载器、扩展类加载器等
- 所有被同步锁（`synchronized`）持有的对象：被 `synchronized` 关键字锁住的对象
- 反应 JVM 内部情况的特殊对象
	- JMXBean：用于 JVM 监控和管理的 MXBean
	- JVM TI 中注册的回调：用于调试和性能分析的工具接口回调
	- 本地代码缓存：JIT 编译器生成的本地代码缓存、方法区中的代码数据等

## 5  什么情况下类会被卸载？

在 Java 中类的卸载条件要比对象严格得多。同时满足以下三个条件的类，才可能被 JVM 卸载：

- 该类的所有实例都已经被回收
- 加载该类的类加载器已经被回收
- 该类对应的 `java.lang.Class` 对象没有在任何地方被引用，无法在任何地方通过反射访问该类的方法

> [!note]
> 即使三个条件全部满足，JVM 也**不一定会**立即卸载该类。类的卸载通常发生在：
> - **Full GC** 期间
> - **元空间（Metaspace）内存不足**时
> - 取决于当前 GC 算法和策略

## 6  强引用、软引用、弱引用是什么？有什么区别？

### 6.1  强引用

强引用是最常见的引用方式，即通过 `new` 关键字创建变量并赋值给变量

```java
Object obj = new Object();
```

- 回收时机：只要有强引用指向该对象，GC 将永远不会回收该对象。
- 特点：当内存不足时，JVM 宁愿抛出 `OutOfMemoryError`，也不会强制回收对象
- 释放：只有将该引用显式置为 `null`，或者是让引用超出作用域，对象才可能被回收。但具体回收时机，是要看垃圾收集策略的。

### 6.2  软引用

通过 `java.lang.ref.softReference` 类实现

```java
SoftReference<Object> softReference = new SoftReference<>(new Object());
```

- 回收时机：当 JVM 内存不足时 (即将抛出 OOM 前)，GC 会回收软引用指向的对象。
- 特点：
	- 适合用于内存敏感的**高速缓存**，如图片缓存、页面缓存等
	- 只要内存充足，软引用对象会保留；
	- 内存紧张时，先回收软引用再尝试分配内存。
- 用途：提升性能的同时，避免内存溢出。

### 6.3  弱引用

通过 `java.lang.ref.WeakReference` 类实现

```java
WeakReference<Object> weakReference = new WeakReference<>(new Object());
```

- 回收时机：不管内存是否充足，只要发生 GC，弱引用都会被回收。
- 特点：
	- 比软引用更容易被回收
	- 常用于解决内存泄露问题
- 用途：
	- 维护非强制性的映射关系，避免被长生命周期对象导致内存泄露 。
	- 同样可以用来实现缓存。

### 6.4  虚引用

通过 `java.lang.ref.PhantomReference`

```java
PhantomReference<Object> phantomRef = new PhantomReference<>(new Object(), new ReferenceQueue<>());
```

- 作用：
	- 跟踪对象的回收状态，它允许你在对象被回收后执行一些资源释放或后处理逻辑。
	- **无法通过虚引用获取对象**：`get()` 方法始终返回 `null`（这是它与其他引用的最大区别）。
		- 因此，它不会阻止对象被回收，因此是安全的内存管理工具。
	- **GC 决定回收对象时，虚引用会被放入引用队列（`ReferenceQueue`）**。
		- 虚引用入队是在 GC 决定回收对象时发生的，但具体何时回收仍然由 GC 决定，不一定是立即回收的。
- 特点：
	- 主要用于**对象回收跟踪**，而不是访问对象
	- 通常结合 `ReferenceQueue` 使用，在对象被回收后收到通知
	- 清理操作必须是由外部线程，通过轮询或阻塞的方式来主动执行，而不是由 JVM 自动触发。具体见 [[#6.6  引用队列 ReferenceQueue]]
- 用途：
	- 在对象被回收后执行清理操作，如释放 Native 内存。

### 6.5  四种引用对比

| 引用类型    | 回收时机             | `get()` 返回值     | 典型用途                                  |
| ------- | ---------------- | --------------- | ------------------------------------- |
| **强引用** | 从不回收（除非主动置 null） | 返回对象本身          | 普通对象引用                                |
| **软引用** | 内存不足时回收          | 返回对象（可能已回收）     | 缓存（图片、文件等）                            |
| **弱引用** | 发生 GC 时立即回收      | 返回对象（可能已回收）     | 避免内存泄漏（如 `ThreadLocal`、`WeakHashMap`） |
| **虚引用** | 对象回收时，虚引用入队      | **始终返回 `null`** | 资源回收跟踪（如 NIO 堆外内存）                    |

### 6.6  引用队列 ReferenceQueue

- 软引用、弱引用和虚引用都可以可选地关联一个 `ReferenceQueue`
- 对象被回收时，对应的引用对象会被 JVM 自动放入引用队列。
- 开发者可以通过轮询或阻塞的方式，从队列中获取引用，从而得知对象已被回收，进而执行后续清理逻辑。

```java
Reference<Object> queue = new ReferenceQueue<>();
WeakReference<Object> weakRef = new WeakReference<>(new Object(), queue);

// 模拟 GC
System.gc();

// 检查队列中是否有被回收的引用
Reference<?> ref = queue.poll();
if(ref != null){
	System.out.println("对象已被回收！");
}
```

## 7  Java 中的 GC，分别作用在什么范围

### 7.1  新生代收集 Minor GC / Young GC

- 作用范围：新生代的内存
- 触发条件：当 Eden 区空间不足时触发
- 特点
	- 频率较高，速度较快
	- 通常采用 **复制算法**
	- 会触发 Stop-The-World(STW)，暂停所有应用线程
- 流程
	- Minor GC 将 Eden 区和一个 Survivor 区中的存活对象复制到另一个 Survivor 区，并清空 Eden 区和原 Survivor 区。
	- 如果 Survivor 区无法容纳存活对象，则通过分配担保机制将多余对象直接晋升到老年代。

### 7.2  老年代收集 Major GC / Old GC

- 作用范围：老年代的内存
- 触发条件：老年代空间不足时触发
- 特点
	- 通常速度慢于 Minor GC
	- 通常采用的算法
		- **标记 - 清除（Mark-Sweep）**
		- **标记 - 整理（Mark-Compact）**

### 7.3  整堆收集 Full GC

- 作用范围：整个 Java 堆以及方法区的内存
- 触发条件
	- 老年代空间不足
	- 方法区空间不足
	- 调用 `System.gc()`（JVM 不保证立即执行）
	- Minor GC 晋升失败
- 特点
	- 开销最大，耗时最长
	- 会触发完整的 STW，严重影响应用响应时间
	- 应尽量避免频繁 Full GC。

### 7.4  混合收集 Mixed GC

- 作用范围：整个新生代加部分老年代内存
- 触发条件：由 G1 GC 在特定阶段触发
- 特点
	- 目前只有 G1 GC 支持 Mixed GC
	- 目标是避免 Full GC 的长停顿

## 8  堆内存的分配策略

- 对象优先在 Eden 分配
	- 大部分情况下，新创建的对象在新生代 Eden 区分配内存
	- 当 Eden 区空间不足时，JVM 会触发一次 Minor GC
- 大对象直接进入老年代
	- 大对象是指 **需要连续内存空间** 的对象，典型代表是 **长字符串** 和 **大数组**。
	- 通过 JVM 参数 `-XX:PretenureSizeThreshold` 设置阈值（单位：字节），超过该值的对象直接在老年代分配。
		- 该参数只在 **Serial** 和 **ParNew** 垃圾回收器下有效。
		- 在 G1 回收器中，大对象（超出 Region 大小的一半）会分配在 巨型区 (Humongous Region) 中。
- 长期存活的对象进入老年代
	- 每个对象在新生代中，都有一个 **年龄计数器**，每经历一次 Minor GC 并存活下来，年龄就增加 1 岁。
	- 当年龄达到阈值时，晋升到老年代。
	- 通过 JVM 参数 `-XX:MaxTenuringThreshold` 设置年龄晋升阈值，通常默认 15。
- 动态对象年龄判断
	- 年龄晋升的阈值，并非固定为 `-XX:MaxTenuringThreshold`，JVM 会根据 Survivor 区实际使用情况进行动态调整。
	- 判断逻辑：
		- JVM 会统计 Survivor 区中 **相同年龄的所有对象的大小总和**。
		- 如果 **某个年龄的对象总和超过了 Survivor 区空间的一半**，则这个年龄就是年龄晋升的阈值
		- 大于等于该阈值的对象将直接晋升到老年代，而不再等待达到 `-XX:MaxTenuringThreshold`

### 8.1  空间分配担保

#### 8.1.1  经典空间分配担保流程

- 第一次检查：判断是否 `老年代最大连续空间 > 新生代所有对象总大小`
	- 是，则直接进行 `Minor GC`
	- 否，则进入下一步判断
- 第二次检查：判断是否 `-XX:HandlePromotionFailture` 的值允许担保失败
	- 是，则进入下一步判断
	- 否，则直接进行 `Full GC`
- 第三次检查：判断是否 `老年代最大连续空间 > 新生代历次晋升到老年代的平均大小`
	- 是，则进行 `Minor GC`
	- 否，则进行 `Full GC`

![经典空间分配担保流程](img/3-垃圾回收策略/经典空间分配担保流程.md)

#### 8.1.2  简化逻辑 l

JDK 6 开始，`-XX:HandlePromotionFailture` 参数不再生效，JVM 总假设允许担保失败。因此，逻辑简化为

![简化的空间分配担保流程](img/3-垃圾回收策略/简化的空间分配担保流程.md)

```text
if 老年代连续空间 > 新生代所有对象总和
	then 执行 Minor GC;
else if 老年代最大连续空间 > 历次晋升的平均大小
	then 执行 Minor GC（有风险）;
else
	then 执行 Full GC;
```

- 风险：如果晋升失败，则触发 Full GC

## 9  new 创建的对象一定在 Java 堆中吗？局部变量是基本类型创建在哪？如果成员变量是基本类型呢？

### 9.1  new 创建的对象一定在 Java 堆中吗？

- 不一定。
- 绝大多数情况下，`new` 创建的对象是分配在 **Java 堆** 中的，因为堆是 JVM 管理对象实例的主要区域。
- 但在特定情况下，JVM 会把对象分配到栈上，也就是 **栈上分配**。
- 栈上分配的条件：逃逸分析
	- 逃逸分析是一种 JVM 的分析技术，用于判断一个对象的作用域是否仅限于当前方法内部
	- 如果 JVM 证明该对象不会逃逸，则 JVM 可以将其分配在 **栈帧的局部变量表** 中。
	- 不会逃逸，也就是该对象既不会被方法外部访问，不会被其他线程引用，也不会作为返回值返回
- 栈上分配的对象，其生命周期随方法调用创建，在方法结束时，通过弹出栈帧而自动销毁，无需 GC 介入。

### 9.2  局部变量是基本类型，创建在哪？

基础类型的局部变量存放在 **Java 虚拟机栈** 中。

- 每个线程都有独立的虚拟机栈，栈帧对应方法调用
- 在栈帧的 **局部变量表** 中，基本类型的值 **直接存储**，而非存储引用

### 9.3  成员对象是基础类型，创建在哪？

基本类型的成员变量 **与对象关联**，对象被分配到哪，其成员变量就被分配到哪

- 一般存储在 Java 堆上
	- 静态成员和常量成员一定在堆上
- 在 JIT 优化（逃逸分析 + 标量替换）生效时，对象的字段也可能被才散到栈上。

## 10  Java 堆内存详细讲解，为什么要这么划分，每一个区域用的什么垃圾回收算法？

### 10.1  Java 堆的划分

Java 堆内存通常分为两个大区域：

- 新生代
	- 主要用于存放新创建的对象
	- 通常被分为 Eden 区和 Survivor 区
	- 分配逻辑
		- 当对象被实例化时，它们首先被分配到 Eden 空间。
		- 经过一段时间，如果对象仍存活，则会被移动到 survivor 区
		- 当达到年龄阈值后，仍然存活的对象将会晋升到老年代
- 老年代
	- 主要用于存放存活时间较长的对象，例如全局变量、静态变量等
	- 当新生代中的对象，经过多次垃圾回收后仍然存活，就会晋升到老年代
	- 对于较大的对象，会直接分配到老年代中

### 10.2  划分的原因

- 优化内存分配：新建对象较频繁且短命，使用不同的区域进行划分，可以提高内存分配的效率
- 提高垃圾回收效率：根据对象的生命周期长短，使用不同的算法，可以最大程度提高垃圾回收的效率，减少程序停顿时间和开销

### 10.3  垃圾回收算法

- 新生代：新生代主要用于存放声明周期较短的对象，使用 **复制算法** 进行垃圾回收。
	- 这种算法能够快速定位和回收大部分的瞬时对象，减少空间碎片和内存分配时的复杂性
- 老年代：主要采用 **标记 - 清除算法** 和 **标记 - 整理算法** 进行垃圾回收。
	- 这种算法适合存活周期长的对象，避免由于频繁复制长生命周期对象导致的性能问题

## 11  垃圾回收算法有哪些？

垃圾回收算法主要有四种：复制算法、标记 - 清除算法、标记 - 整理算法、分代收集算法。

### 11.1  复制算法

- 半区复制
- 算法流程
	- 每次将内存分为大小相等的两份，每次使用其中一块。
	- 当使用内存满了时，就进行垃圾回收。
- 特点：实现简单，运行高效，但可用内存缩小为了之前的一半，浪费内存空间

### 11.2  标记 - 清除算法

- 首先利用可达性遍历内存，把存活对象进行标记。
- 标记结束后，统一将非存活垃圾对象回收。
- 特点：算法效率低，会产生大量不连续的空间碎片。

### 11.3  标记 - 整理算法

- 根据老年代的特点提出的标记算法
- 流程：
	- 首先，利用可达性遍历内存，把存活对象进行标记（和标记清除算法一致）
	- 然后，在标记结束后，将所有存活对象朝一端移动
	- 最后，直接清理掉边界以外的内存

### 11.4  分代收集算法

根据各个年代的特点采用最适当的垃圾回收算法

- 新生代采用复制算法
- 老年代采用标记 - 清除算法或标记 - 整理算法

## 12  有哪些垃圾回收器？

主要有 7 种垃圾回收器

| 垃圾回收器             | 串行/并行/并发 | 新生代/老年代 | 垃圾回收算法           | 目标     | 适用场景                          |
| ----------------- | -------- | ------- | ---------------- | ------ | ----------------------------- |
| Serial            | 串行       | 新生代     | 复制算法             | 响应速度优先 | 单 CPU 环境下的 Client 模式          |
| Serial Old        | 串行       | 老年代     | 标记 - 整理算法        | 响应速度优先 | 单 CPU 环境下的 Client 模式          |
| ParNew            | 并行       | 新生代     | 复制算法             | 响应速度优先 | 多 CPU 环境下的 Server 模式中与 CMS 配合 |
| Parallel Scavenge | 并行       | 新生代     | 复制算法             | 吞吐量优先  | 在后台运算而不需要太多的交互任务              |
| Parallel Old      | 并行       | 老年代     | 标记 - 整理算法        | 吞吐量优先  | 在后台运算而不需要太多的互动任务              |
| CMS               | 并发       | 老年代     | 标记 - 清除算法        | 响应速度优先 | 集中在互联网站或 B/S 系统服务端上的 Java 应用  |
| G1                | 并发       | both    | 复制算法 + 标记 - 整理算法 | 响应速度优先 | 面向服务端应用，CMS 的升级产品             |

垃圾收集器是和具体的 JVM 实现紧密相关的，不同厂商、不同版本的 JVM，提供了不同的选择。

### 12.1  Serial GC

- Serial GC 是最古老的版本，采用了 **复制算法**。
- 其收集工作是单线程的，在垃圾收集的过程中会进入 STW(Stop-The-World) 状态
- 特点：精简的 GC 实现，无须维护复杂的数据结构，初始化简单，是 Client JVM 的默认选择
	- 好处：简单高效，内存消耗少，没有线程交互的开销，单线程收集效率高
	- 缺点：在进行垃圾回收时，会触发 STW，用户体验不好
- 对应 JVM 参数是 `-XX:+UseSerialGC`

#### 12.1.1  Serial Old

- 是 Serial GC 的老年代实现，采用了 **标记 - 整理算法**。

### 12.2  ParNew GC

- 是新生代 GC 实现
- 实际上是 Serial GC 的多线程版本
- 最常见的应用场景是配合老年代的 CMS GC 一同进行垃圾回收
- 对应 JVM 参数是 `-XX:+UseParNewGC`

```bash
# ParNew 配合 CMS
-XX:ConcMarkSweepGC -XX:+UseParNewGC
```

### 12.3  Parallel GC

- JDK 8 版本中，是 Server 模式 JVM 的默认 GC 选择
- 是 **吞吐量优先** 的 GC
- 算法和 Serial GC 比较相似
- 特点：吞吐量优先，在新生代和老年代都可以并行收集，允许多个垃圾回收线程同时运行，降低垃圾收集时间，提高吞吐量。
- JVM 参数是 `-XX:+UseParallelGC`
- 还存在一些开发者友好参数：
	- `-XX:MaxGCPauseMillis=value`：控制最大垃圾收集停顿时间
		- 参数的值是一个大于 0 毫秒数，收集器将尽量保证内存回收花费的时间不超过用户设定值
	- `-XX:GCTimeRatio=N`：设置吞吐量大小
		- GC 时间和用户时间比例 = 1/(N+1)

### 12.4  CMS GC

- 基于 **标记 - 清除算法**
- 设计目标是 **尽可能减少用户线程的停顿时间**
	- 适用于 Web 等反应时间敏感的应用
- 特点：
	- 采用标记 - 清除算法，存在内存碎片化问题，所以难以避免在长时间运行等情况下的 Full GC，导致恶劣的停顿。
	- 由于并发，CMS 会占用更多 CPU 资源，并和用户线程争抢

### 12.5  G1 GC

#### 12.5.1  概念与定位

**G1（Garbage-First Garbage Collector）** 是 HotSpot 虚拟机中一款**兼顾吞吐量和停顿时间**的垃圾回收器，从 **Oracle JDK 9 起成为默认 GC**。

> [!note] 与 CMS 的差异
> 相对于 CMS，G1 无法达到 CMS 的最佳情况，但最差情况要改善很多。
 v
- 这是一种兼顾 **吞吐量和停顿时间** 的 GC
- 是 Oracle JDK 9 以后默认的 GC 选项
- 相对于 CMS GC，G1 没法到达 CMS GC 的最好情况。但是，最差情况要改善很多。
- 具体内容：
	- G1 GC 虽然还有年代的概念，但不同于传统回收器将内存分为连续的三块的情况，G1 将整个堆内存均匀地切分成约 2048 块。
	- 每一块都是一个 Region，每个 Region 的大小通常是 `1~32MB` 之间（2 的幂次方）
	- 可以通过 JVM 参数 `-XX:G1HeapRegionSize` 设定。如果不设置，JVM 会根据堆大小自动计算
	- 虽然每一个 Region 是物理平等的，但是在 G1 运行过程中，不同的 Region 会被动态赋予不同的逻辑角色：
		- Eden：新对象优先分配到这里
		- Survivor：Minor GC 后存活的对象复制到这里
		- Old：长期存活或大对象存放地方
		- Humongous：专门存放巨型对象的特殊 Region
	- 相对于经典分区，在 G1 GC 中新生代和老年代不再需要物理上连续的内存块。

## 14  Java 对象的内存布局

Java 内存中的对象以下三部分组成：

- 对象头
- 实例数据
- 对齐填充字节

### 14.1  对象头

对象头由以下三部分组成

- mark word
- 指向类信息的指针
- 数组长度（数组才有）

#### 14.1.1  mark word

存储内容

- 对象的哈希码：用于支持 `Object.hashCode()` 方法
- GC 分代年龄：用于判断对象是否晋升为老年代
- 锁标志位：记录对象的锁状态，无锁、偏向锁、轻量级锁、重量级锁
- 偏向线程 ID：当线程处于偏向锁状态时，持有锁的线程 ID
- 偏向时间戳：偏向锁时间信息

#### 14.1.2  执行类信息的指针 Class Pointer

作用：指向方法区中的类元数据，表示该对象所属的类

### 14.2  实例数据

- Java 对象的属性和值存储。也就是，对象中所定义的非静态成员
	- 基础类型字段
	- 引用类型字段
- 排列顺序：由 JVM 分配策略决定，通常
	- 按字段大小从大到小排列，以减少内存填充。
	- 父类字段先于子类字段

### 14.3  对齐填充字节

- JVM 要求 **Java 对象的大小必须是 8 字节的整数倍**。如果对象头 + 实例数据的大小不是 8 的倍数，则通过填充字节补齐。

#### 14.3.1  内存对齐的主要作用是

- 平台原因：
	- 不是所有硬件平台都支持 **任意地址访问任意类型的数据**。
	- 某些硬件平台只能在某些地址取特定类型的数据，否则抛出硬件异常。
- 性能问题：经过内存对齐后，CPU 的内存访问速度大大提升。
	- 现代 CPU 以缓存行为单位读取内存（通常为 64 字节）
	- 对齐的对象可以更好地利用 CPU 缓存，减少因跨缓存行读取带来的性能损失
	- 未对齐的对象更容易跨行。因此，未对齐的对象可能需要 **两次内存访问** 才能完整读取，而对齐的对象仅需一次。

## 15  String 保存在哪里呢？

String 对象的创建，一般是通过两种方式

```java
String s1 = "xxx";

String s2 = new String("xxx");
```

### 15.1  方式 1：`String s1 = "xxx";`

- **查找常量池**：JVM 会去字符串常量池（String Constant Pool）中查找是否存在内容为 `"xxx"` 的字符串对象。
- **存在**：直接返回该对象的引用，赋值给 `s1`。
- **不存在**：在**堆**（JDK 7+，JDK 6 是永久代）中创建一个 `"xxx"` 对象，并将其引用放入常量池，再返回该引用给 `s1`。

**结果**：`s1` 指向的是**字符串常量池中的那个对象**（也是堆中的对象，但被常量池引用）。

### 15.2  方式 2：`String s2 = new String("xxx");`

- **第一步（同方式 1）**：JVM 会先去字符串常量池中查找/创建 `"xxx"` 对象，获得它的引用（记作 `refPool`）。
- **第二步（`new`）**：在**堆**中**创建一个新的 String 对象**，该对象内部会存储 `refPool`（即底层字符数组的引用，或者将内容复制过去，具体取决于 JDK 版本，但在逻辑上可以理解为新对象引用了常量池中的字符串内容）。
- **第三步（赋值）**：将这个新对象的引用赋值给 `s2`。

**结果**：`s2` 指向的是**堆中 `new` 出来的新对象**，而该对象的内容与常量池中的 `"xxx"` 相同，但二者**地址不同**。

### 15.3  内存分布

| 变量 | 存储在 | 指向的内容 | 说明 |
|:---|:---|:---|:---|
| `s1` | 栈帧的局部变量表 | 字符串常量池中的 `"xxx"` 对象（堆） | 直接指向常量池缓存的对象 |
| `s2` | 栈帧的局部变量表 | 堆中 `new` 出来的新 String 对象 | 该对象内部持有常量池 `"xxx"` 的引用 |
| `"xxx"` 字面量对象 | 堆（常量池区域） | 实际的字符数据 | JDK 7+ 常量池也在堆中 |
| `new String()` 对象 | 堆（普通区域） | 自己的对象头、字段等 | 是一个独立对象，非常量池 |

### 15.4  字符串常量池的位置

- **JDK 1.6 及之前**：字符串常量池位于**方法区（永久代）**，字面量对象存储在永久代。
- **JDK 1.7 开始**：字符串常量池**移到 Java 堆**中，字面量对象存储在堆中。

字符串常量池中的字面量对象在 JDK 7+ 位于堆中，而 `new` 出来的对象也一定在堆中，二者都在堆，但属于不同的逻辑区域。

### 15.5  创建了几个对象？

- **方式 1**（`String s1 = "xxx";`）：如果常量池中没有 `"xxx"`，则创建 **1 个对象**（常量池中的 `"xxx"`）；如果已有，则 **0 个**。
- **方式 2**（`String s2 = new String("xxx");`）：无论常量池是否已存在 `"xxx"`，`new` 都会创建一个新对象。因此至少创建 **1 个（new 出来的）**，最多 **2 个（若常量池中没有，则先创建字面量对象，再 `new` 一个）**。

### 15.6  总结

- `s1` 直接指向**常量池中的字符串对象**。
- `s2` 指向**堆中的新 String 对象**，该对象内部引用了常量池中的字符串内容。
- 两种方式都涉及 **栈（引用）** 和 **堆（对象）**，但 `s1` 的引用指向的是常量池管理的对象，而 `s2` 的引用指向的是普通堆对象。

## 17  `String s = new String("abc")` 执行过程中涉及的内存区域

### 17.1  回答

> [!note]
> - `String s = new String("abc")` 涉及栈（存储变量引用）、堆（存储 new 对象和 JDK 7+ 的常量池字符串）、方法区/元空间（存储类元数据）。  
> - 创建的对象数量为 1 个或 2 个，取决于字符串常量池中是否已存在 `"abc"`。  
> - 若为首次执行，则先在常量池中创建 `"abc"`，再通过 `new` 创建新对象；若已存在，则仅 `new` 创建一个新对象。

### 17.2  代码执行步骤

#### 17.2.1  第 1 步：处理字符串字面量 `"abc"`

- JVM 首先去 **字符串常量池（String Constant Pool）** 中查找是否已存在内容为 `"abc"` 的字符串对象。
- **若不存在**：JVM 会在 **堆（Heap）** 中创建一个 `"abc"` 字符串对象，并将其引用存入字符串常量池（相当于缓存）。
- **若已存在**：直接返回该对象的引用，不会重复创建。

> [!note] **版本差异**：
> - JDK 1.6 及之前：字符串常量池位于 **方法区（永久代）**，因此 `"abc"` 对象存储在永久代。
> - JDK 1.7 及之后：字符串常量池移至 **Java 堆**，因此 `"abc"` 对象存储在堆中。

#### 17.2.2  第 2 步：执行 `new String()`

- 通过 `new` 关键字，JVM 在 **堆（Heap）** 中**创建一个新的、独立的 String 对象**。
- 该对象的构造方法会接收上一步从常量池中获取的 `"abc"` 引用（作为参数），从而完成初始化。
- 这个新对象与常量池中的对象**不是同一个对象**（地址不同），但内容相同。

#### 17.2.3  第 3 步：变量赋值

- `String s` 是一个**局部变量**，存储在 **虚拟机栈（VM Stack）** 的局部变量表中。
- 该变量存储的是第 2 步中 `new` 出来的 String 对象的**引用地址**，而非对象本身。

### 17.3  涉及的内存区域汇总

| 内存区域 | 存储内容 | 说明 |
|:---|:---|:---|
| **虚拟机栈（Stack）** | `s` 变量（引用地址） | 局部变量 `s` 存储的是堆中 `new String()` 对象的地址 |
| **Java 堆（Heap）** | ① `new String()` 创建的对象<br>② `"abc"` 字符串对象（JDK 7+） | 所有 `new` 创建的对象都在堆中；<br>字面量 `"abc"` 在 JDK 7+ 也存储在堆中（常量池） |
| **方法区 / 元空间（Metaspace）** | String 类的元数据 | 存储 `String` 类的类型信息、方法信息等 |
| **运行时常量池（JDK 1.6 及之前）** | `"abc"` 字符串对象（在永久代中） | JDK 1.6 以前字符串常量池位于永久代，JDK 1.7+ 已移至堆中 |

### 17.4  创建了几个对象？

通常答案是 **1 个或 2 个**，取决于字符串常量池中是否已存在 `"abc"`：

#### 17.4.1  情况一：常量池中 **不存在** `"abc"`

- **2 个对象**：
  1. **字面量对象**：为满足 `"abc"` 字面量，在堆中（或 JDK 1.6 的永久代）创建的对象，并被放入字符串常量池。
  2. **`new` 对象**：通过 `new` 在堆中创建的独立 String 对象。

#### 17.4.2  情况二：常量池中 **已存在** `"abc"`

- **1 个对象**：
  1. 仅 `new` 关键字在堆中创建了一个新的 String 对象。
  2. 常量池中的 `"abc"` 对象在之前已经创建过，此时直接复用其引用，不会新建。

# 什么是高负载？

**高负载**是指系统在单位时间内需要处理的任务量（并发量或数据量）远超其常规处理能力，但通过合理的架构设计，仍能保证任务**不积压、不丢失、不崩溃**，且系统保持稳定运行的状态。

# 难点分析

由于真实业务中，定时任务的使用十分常见。因此，随着接入业务的增加，**任务量暴涨**，会给系统带来数据存储、检索、执行、触发时效等多方面挑战。

# 解决思路和方法

## 1  应用层面减少任务量

对于同一业务方、同一时间的多个任务，应该合并为一个 " 计划列表 "，然后为这个 " 计划列表 " 创建一个定时任务，而不是为每一个单独任务都创建一个定时任务。

## 2  分库分表

分库分表是指将一个大型数据库分为多个较小的库（分库），并将每个数据库的数据进一步分为多个较小的表（分表），每个表只包含部分数据。

这种方式使得查询和更新操作可以在多个数据库和表之间并行执行，提升了系统的扩展性和性能。

### 2.1  垂直分表

垂直分表是指将原始数据按照列拆分为多个表，每个表只包含某些列。

- 适用场景：表中包含大量无关字段，或存在冷热数据。
- 示例：将用户信息表和订单信息表分离；将任务基础信息与任务执行日志分离。

### 2.2  水平分表

水平分表是指将原始数据按照行拆分为多个表，每个表只包含某些行。

- 适用场景：单表数据量过大
- 示例：将订单信息按照订单号的哈希值分散到多个表中；将任务按照 `task_id` 哈希值或时间范围分片。

### 2.3  分库分表组合

分库分表组合是指将垂直分表和水平分表结合起来，同时对数据库和表进行切分。

- 示例：一个包含用户信息和订单信息的表，先按业务垂直拆分（用户库、订单库），再在每个库内按 ID 哈希水平分表，最终分散到多个数据库实例中。

## 3  数据分区

数据分区的理念和分库分表类似，都是期望将数据拆分后，通过提升并发度，从而提升检索效率。区别是：

- 数据分区表（Partitioning）：逻辑上是一张表，物理上按规则存储多个文件。对应用透明，无须修改代码。
- 分库分表（Sharding）：物理上将单表拆分为多个独立的库和表，逻辑上也是多个独立库和独立表。因此，需要应用层或中间件的支持。

**数据分区还可以运用在缓存层：**

- 对 Redis 中的数据做数据分区（如 Redis Cluster 分片），将不同 key 分散到不同节点，提升缓存吞吐量。
- 注意热点 Key 问题，避免单一分片过载。

## 4  线程池技术

通过提高系统的并发度来解决任务过多的问题。

线程池是很好的方案：

- **批量任务并发执行**：提升系统吞吐量。
- **线程管理能力**：复用线程、控制并发数、避免频繁创建销毁线程

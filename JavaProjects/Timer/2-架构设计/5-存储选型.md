## 关系型数据库

常用的关系型数据库有 MySQL、Oracle、SQLServer、TDSQL 等。

### 核心优点

1. 可靠性强：数据持久化在磁盘上，无丢失风险。
2. 结构规范清晰：列有格式/长度规范，同行数据属性严格一致。
3. 支持事务：满足 " 要么同时成功，要么同时失败 " 的原子性操作需求。

### 缺点

1. 性能普遍不高：受限于按行存储、维护索引、事务等开销，速度较慢。
2. 表结构扩展极不方便：上线后增减字段会对线上环境产生影响。

### 对比

| 特性   | MySQL         | Oracle        | SQLServer | TDSQL  |
| ---- | ------------- | ------------- | --------- | ------ |
| 运行平台 | Linux/Windows | Linux/Windows | Windows   | Linux  |
| 扩展性  | 单机            | 单机            | 单机        | 分布式    |
| 性能   | 几千级           | 几千级           | 几千级       | 分布式可扩展 |
| 价格   | 正常            | 昂贵            | 正常        | 十分昂贵   |

## 非关系型数据库 (NoSQL)

这里主要指以键值对为存储形式的非关系型数据库，常用的有 Redis、Memcache 等。

- 优点：**性能极高**。基于内存存储，KV 结构，读写速度十分快。
- 缺点：**不可靠（易丢数据）**。由于数据基于内存存储，缺乏强持久化保证。对于重要数据，不建议用此类 NoSQL 存储。

## xTimer 存储数据分析

本项目为分布式定时服务，首先要考虑到两种数据需要存储：

1. 定时任务 (Task)：业务调接口时创建的一个定时任务，需求中包含运行 `cron` 表达式，以及任务执行成功后如何回调等信息。
2. 单词触发任务 (Job/Instance)：一个 `cron` 表达式属于一个周期性任务 (例如每天早上 9 点触发)。那么，单个定时任务在整个周期内会多次触发。也就是说，一个定时任务最终会转化为多个单次触发任务进行存储。

## 核心存储选型

- 排除 NoSQL：定时任务数据有极高的精准性、持久化要求，且需要支持事务，故排除所有 NoSQL。
- 排除 SQLServer：项目需要运行在 Linux 上，直接排除 Windows 专属的 SQLServer。
- 排除 TDSQL：功能上与 MySQL 相似（腾讯分布式版 MySQL），但价格十分昂贵，出于性价比考虑排除。
- 排除 Oracle：主要用于传统工业场景且昂贵，互联网场景下 MySQL 更为通用。

> 最终结论
> 选择 MySQL 作为项目使用的数据库。

## 数据处理加速需求

### 项目要求

本项目对数据有两个严苛的要求：

1. 一个定时任务在整个生命周期中，需要频繁的对其进行查询和删除操作；
2. 为了应对高负载需求，需要对数据进行横向/纵向的分治操作。

因此，纯关系型数据库无法满足如此高频的内存级操作。这里必须引入 NoSQL 作为加速层。

### NoSQL 选型

在两种 NoSQL 的选择上，相比于 Memcache，**Redis 的数据结构更为丰富**（如 ZSet 有序集合完美契合定时任务排序需求），且生态更为主流。

> 最终结论
> 采用 **MySQL + Redis 的二级存储架构**。MySQL 负责持久化与事务，Redis 负责高频查询与分片调度加速。

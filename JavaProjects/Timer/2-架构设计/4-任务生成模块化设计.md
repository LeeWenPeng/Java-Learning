# migrator 模块
## 1  二级存储模型 + 迁移器模块

xTimer 基于 MySQL 和 Redis 建立二级存储模型，并增设一个迁移器模块（migrator module），**根据任务执行时机由近及远进行存储介质之间的迁移同步**。

迁移机制

1. 时间步长推移：迁移器模块每间隔一个时间步长，处理下一个时间步的内容。_(例如：步长设为 `60 min`，当前 `11:00`，则处理 `12:00 ~ 13:00` 的任务)_。
2. **全量扫描和打点**：全量扫描 MySQL 中的定时器任务定义库，解析出即将执行的任务列表。在 MySQL 任务执行记录表中添加记录，并在 Redis 中批量打点。
3. 二级存储兜底：触发器轮询时会优先查询 Redis。只有当 Redis 集群中出现分片数据丢失时，才查询 MySQL 兜底。

## 2  打点策略演进

### 2.1  串行打点方案

#### 2.1.1  工作模式

- 首次打点：定时器在激活时，首先推算出首次执行的定时任务并存入 Redis ZSet。
- 后续打点：前一个定时任务执行完成后，由**执行器模块**打下当前任务的点。

#### 2.1.2  方案分析

1. 优点：节省存储资源，一定程度上缓解超长过期时间导致的缓存资源浪费问题。
2. 缺点：强依赖前置任务。每次执行前都需要等待前一个点被唤醒并执行完，才能打下个点。无法支持短间隔、高频次的任务执行。

### 2.2  优化方案：批量打点

基于定时器中关于执行时间的定义（cron expr），推算出一整个批次的执行时间，并进行批量打点，以此解决串行打点的弊端。

#### 2.2.1  方案分析

> [!BUG] 问题一：基于 cron 表达式推算出的执行时间点可能漫无边际
> 解决方案：明确批量打点的边界，将该时间范围定义为一级时间步 `step1`。之后，每隔一个 `step1` ，就完成对下一个一级时间步内的定时任务进行批量打点。

> [!BUG]+ 问题二：用户可能反复对定时器状态进行修改，导致频繁对批量的点进行修改，复杂度和工作量都大大提升。
> 解决方案：双原则约束
> - 原则一（定义不可变）：明确定时器创建后不允许修改定义，只允许激活和去激活操作。要修改只能通过删除旧定时器，重新创建新定时器的方式
> - 原则二（只打点不删点）：倘若用户将已经完成打点动作的定时器置换为去激活态，将不删除该点，而是留待该点被唤醒后，由执行器在查询定时器详情时，进行状态的合法检查，从而规避无效执行。

# 主动轮询

> 核心思路：实现定时器最简单粗暴的方式：`轮询 + 触发`。

1. 注册定时器: 解析并将定时任务平铺展开，明确记录每笔任务的执行时间。
2. 节点自轮询：每间隔一个微小的时间窗口（如 1s），对定时任务列表进行**全量查询**。
3. 过滤与触发：以 `执行时间 ≤ 当前时刻` 为过滤条件，捞出符合条件的任务并执行。

# 优化一：存储结构优化(有序表)

> 目标：基于有序表提升查询效率

对于无序表，插入记录是 `O(1)` 的时间复杂度，但每次查询是 `O(N)` 级别的线性查询。优化方向是将时间复杂度均摊到操作中。

例如，使用红黑树或跳表，能以将插入的时间复杂度由 `O(1) -> O(logN)` 为代价，换取查询时间复杂度由 `O(N) -> O(logN)` 的优化。

在 xTimer 的实现中，以 **Redis ZSet** 作为存储介质，以**定时任务执行时间的时间戳为 Score** 进行有序结构的搭建。具体来说，

1. 添加任务：每次添加定时任务时，执行 `ZAdd` 动作，以执行时间的时间戳作为排序的键 (`Score`) 进行有序结构的搭建；
2. 查询任务：每次查询定时任务时，执行 `ZRangeByScore` 动作，以当前时刻的时间戳加上一个微小偏移量，作为 Score 的左右边界

> [!Tip] 为什么选择 ZSet 作为定时任务的存储结构？
> ZSet 兼顾了极高的内存利用率和查询性能，具有自适应的底层数据结构。
> - **小数据量场景（节省内存）**：当 ZSet 中元素数量小于 128 且所有元素长度小于 64 字节时，底层使用 **`listpack`（紧凑列表，Redis 7.0+）** 或 **`ziplist`（压缩列表，Redis 7.0-）**。这是一种连续内存结构，极度节省内存。
> - **大数据量场景（追求性能）**：当元素数量大于 128 或某个元素过大时，底层实现会自动切换为 **`跳表（Skiplist） + 哈希表（Dict）`**。
于是，实现查询时间复杂度由 `O(N) -> O(logN)` 的优化.

# 存储结构优化：横向分治

> 目标：通过**时间范围分片**，减少单词查询涉及的任务数量。

虽然有序表解决了排序问题，但是每次查询时，依然是在一个巨大的 `ZSet` 中找。真正的目标是 " 即将执行 " 的任务，而 " 更晚执行 " 的任务是无用的干扰项。

因此，xTimer 通过 " 时间分片 "，将整条时间切分成具有明确边界的时间片段，从而将任务分散到逐个时间片内。本项目中，选用 **1 min** 作为分片的时间范围。具体来说，

1. 计算表达式：在每次插入定时任务时，根据执行时间推算出所属的分钟级时间范围表达式，例如：`2022-01-12-09:00:00 ~ 2022-01-12-09:01:00`
2. 插入任务：以该表达式为 key，将定时任务插入到不同的 `ZSet` 中，形成相互隔离的有序表。
3. 查询任务：每次查询时，同样根据当前时刻推算出对应表达式，然后到该表达式（key）对应的 `ZSet` 执行 `ZRange` 查询。

从而使得单词查询的任务量级大幅度减少。

# 存储结构优化：纵向分治

> 目标：在时间片的基础上进行分桶，提高并发度

在集群模式下，为了多线程/多节点并发，同时避免临界资源的竞态问题，以分片为最小的资源粒度进行拆解。

因此，也就需要 **将时间分片拆解成更细的粒度**。也就是在**之前横向分治的基础上额外增加一个分桶的维度**。从而保证在每个时间范围内，能有与分桶数相同数量的线程并发参与工作。

具体步骤

1. 第一维（时间）：插入定时任务时，首先根据执行时间，确定其从属的时间范围（分钟级）。
2. 第二维 (分桶)：然后，根据定时任务的唯一标识 `task_id`，结合服务配置的 `最大桶数` ，通过哈希，将任务划分到不同的桶中
3. 组装 Key：以 `时间范围 + 桶号` 组装成一个新的 key，形成二维分片。
4. 插入和查询的步骤和横向分治相同

在经过分片分桶后，将整个定时任务的范围分为了基于时间范围和桶号的二维分片。

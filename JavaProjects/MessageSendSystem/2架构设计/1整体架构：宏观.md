## 1  整体架构

推送服务有三大模块

- 推送接入服务
- 消息中转站
- 推送处理服务

![整体架构](img/1整体架构：宏观/整体架构.md)

## 2  层次结构

推送系统分为四个层次

1. 接入层：包含了负载均衡和网关服务
2. 业务层：需要推送消息的业务，比如电商、云平台、游戏平台等
3. 服务层：推送系统的核心层，有三大模块：推送接入服务、消息中转站、推送处理服务
4. 存储层：通过 MySQL 进行底层存储，通过 Redis 进行对应数据的缓存加速

## 3  上下游服务

在层次关系下，推送流程如下：

1. 当发起一个业务请求时，这个请求首先到达的是负载均衡，负载均衡会将其转发到合适的网关服务，网关服务做了鉴权后，将其传递给业务层。
2. 业务服务做了相关业务后，调用推送接入服务，将需要传送的消息指派到它。
3. 推送接入服务收到消息后，将其存入消息中转站（对消息进行频率上的管控，且方便重试）。触发条件时，消息中转站将消息发送给消息处理服务。消息处理服务获取消息后，通过第三方服务进行推送。
4. 推送完毕后，记录推送事件。也可以进一步对推送数据进行分析，比如成功率、重试率等数据。

### 3.1  服务交互

在系统中，通过 HTTP 接口进行服务之间的交互。

> [!question] 为什么使用 HTTP？
> 因为消息推送系统的瓶颈在于数据库以及第三方推送平台，而不在于接口。因此这里使用 HTTP 这种简单协议会更合适。

#### 3.1.1  对于一个服务多个节点，如果通过 HTTP 发送？

通过负载均衡来进行

两种方式

1. 通过 `Nginx` 组件实现后端多机服务的流量分发。将每个机器都配置在 Nginx 上，当发起业务请求时，直接访问 Nginx 即可，因为 Nginx 会将它收到的请求分发出去。
2. `K8s` 或直接上云，这样直接使用服务名称映射即可。（其底层是服务发现）

### 3.2  存储层

- 使用 MySQL 做底层存储，可靠性保证
- 使用 Redis 做缓存存储，提升性能

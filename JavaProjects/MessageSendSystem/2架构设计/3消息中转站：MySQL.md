## 1  思路

可以使用 MySQL 作为消息中转站。

- 以 MySQL 作为中间存储。消息先存入 MySQL，处理服务再用 SQL 命令从 MySQL 中拉取消息。
- 处理服务使用主从模型，当主节点挂掉了，从节点能够保证功能正常。
	- 主从模型可以通过 MySQL 或 Redis 实现。主节点不断续期，如果主节点长期不续期，则认为主节点挂掉，从而使用从节点取代主节点。类似于一个不断续期的分布式锁。
- 处理服务的拉取动作是串行的，这是为了业务幂等。在多机环境下，如果直接并发拉取消息，会出现多个机器可能会使用相同的 SQL 语句拉取。也就是同一消息被多个节点重复拉取和处理，这是需要避免的。

## 2  消息表设计——中转站消息队列表 `t_msg_queue`

| 字段              | 类型             | 说明                             |
| --------------- | -------------- | ------------------------------ |
| `id`            | `bigint(20)`   | 主键自增 ID                        |
| `msg_id`        | `varchar(256)` | 消息 ID，通过 `uuid` 生成             |
| `to`            | `varchar(256)` | 消息接收者                          |
| `subject`       | `varchar(256)` | 消息主题                           |
| `source_id`     | `varchar(256)` | 业务 ID                          |
| `template_id`   | `varchar(256)` | 模板 ID，使用模板时才有意义                |
| `template_data` | `varchar(256)` | 模板传入参数                         |
| `channel`       | `int(10)`      | 消息类型。1：邮件；2: 短信；3: 飞书          |
| `status`        | `int(10)`      | 消息状态。1: 等待中；2: 处理中；3: 成功；4: 失败 |
| `priority`      | `int(20)`      | 优先级。1：低优先级；2: 中优先级；3: 高优先级     |
| `create_time`   | `datetime`     | 创建时间                           |
| `modify_time`   | `datetime`     | 修改时间                           |

## 3  消息状态（`status`）定义

消息状态分为等待中、执行中、成功、失败

## 4  拉取消息的方式

### 4.1  方案一：直接拉取

推送处理服务直接从 MySQL 中拉取消息，等到消息到达推送处理服务后再进行转换

```SQL
SELECT * FROM `t_msg_queue` 
WHERE (status = 1)
ORDER BY priority, modify_time 
LIMIT 100;
```

- 该方案中，对消息拉取的顺序受到优先级和修改时间影响——先考虑优先级，当优先级相同时，再根据修改时间的早晚进行拉取。
- 因此，该方案存在问题是：当高优先级异常或者较多时，可能会完全阻塞低优先级的消息。

### 4.2  方案二：消息分类

使用三张表，模拟优先级不同的高中低三个消息队列

- `msg_queue_low`：存放普通消息
- `msg_queue_middle`：存放比较重要的消息
- `msg_queue_high`：存放十分要紧的消息

相对于方案一，方案二更适合消息推送系统，原因是：

1. 避免了低优先级消息阻塞
2. 对齐消息队列做中转时的分桶逻辑

## 5  和消息队列做中转站的对比

优点

1. 更少的组件依赖，维护成本低

缺点

1. 吞吐没有消息队列高，当消息创建速度超过 5000 条/s 时不适用
2. 扩展性弱于消息队列。消息队列往往有更丰富的功能，比如 Kafka 自带分片，可以并发拉取消息。但是 MySQL 不行，如果开发相同功能，又会增加很多开发成本。
